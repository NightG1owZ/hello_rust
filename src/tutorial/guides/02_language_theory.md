## 一、所有权心智模型：一张决策图

实践课程：lesson_05（基础）、lesson_14/16/17（组合应用）。

拿到一个值要在函数间传递时，按这个顺序决策：

```
这个类型是 Copy 的吗？（整数、浮点、bool、char、只含 Copy 字段的元组/结构体）
├─ 是 → 隐式按位复制，原变量继续可用，不用想所有权
└─ 否 → 我需要在调用点之后继续使用它吗？
          ├─ 需要 → 借用（&T 只读 / &mut T 独占写）
          │           注意 &mut 同一时刻只能有一个 —— 这是编译器防数据竞争的核心
          └─ 不需要 → move（所有权转移，原变量失效）
                      需要两份独立数据时才 clone（有真实成本）
```

三条铁律（lesson_05 已验证）：

1. 每个值有**唯一**所有者，离开作用域自动释放（RAII）；
2. 赋值/传参对非 Copy 类型是 **move**；
3. 任意时刻：**多个** `&T` **或** **一个** `&mut T`，二者不可兼得。

> 为什么这样设计：内存安全（无悬垂、无重复释放、无数据竞争）在**编译期**用类型系统保证，
> 代价是初学阶段的「与借用检查器搏斗」。搏斗的正确姿势见 [01_learning_method.md](01_learning_method.md) 第三节。

## 二、静态分发 vs 动态分发：成本模型

实践课程：lesson_11（泛型）、lesson_12（dyn）、lesson_14（闭包三态）、lesson_18（宏）。

| 维度 | 静态分发（泛型 / impl Trait） | 动态分发（`dyn Trait`） |
| --- | --- | --- |
| 实现机制 | 单态化：为每个具体类型生成一份代码 | 虚表（vtable）+ 函数指针间接调用 |
| 运行期开销 | 零（与手写代码相同） | 每次调用一次间接跳转；可能阻碍内联 |
| 二进制体积 | 每种用到的类型都膨胀一份 | 只有一份代码 |
| 灵活性 | 编译期确定，一个泛型参数一种类型 | 运行期可混装任意实现者（`Vec<Box<dyn T>>`） |
| 典型场景 | 迭代器链、闭包参数、数学库 | 插件/回调集合、trait object 存储 heterogeneous 类型 |

**选型口诀**：默认静态（编译器还能内联优化）；确需「运行期才确定类型」或「集合混装」才用 dyn。
`Box<dyn Error>`（lesson_10）是动态分发在错误处理上的标准应用：main 只关心「出错了」，不关心具体哪一种。

## 三、Deref 强转链：智能指针为何「像」原生类型

实践课程：lesson_16 示例 3。

```
&Box<String>  --Box: Deref<Target=String-->  &String  --String: Deref<Target=str-->  &str
```

- 编译器在「类型不匹配」时会沿 `Deref` 链自动插入解引用，直到匹配为止；
- 这就是 `char_count(&boxed)`（参数是 `&str`）能直接接受 `&Box<String>` 的原因；
- **注意**：自动解引用适用于方法调用、字段访问、强转位置，**不适用于算术运算符**——
  `*guard * 2` 必须显式写出解引用（lesson_17 示例 5 的 `*count * worker_id`）。

设计启示：函数参数尽量写「最通用的切片形式」——`&str` 而非 `&String`、`&[T]` 而非 `&Vec<T>`，调用方成本最低。

## 四、Send 与 Sync：并发安全的类型系统表达

实践课程：lesson_17 示例 7。

| trait | 含义 | 典型成员 |
| --- | --- | --- |
| `Send` | 值可以**转移**到另一个线程（所有权跨线程移动） | `i32`、`String`、`Vec<T>`、`Arc<T>` |
| `Sync` | `&T` 可以**同时**被多个线程共享（等价于 `&T: Send`） | 不可变数据、`Mutex<T>` |

关键非成员及其原因：

- `Rc<T>`：引用计数是**普通加减法**，两个线程同时 clone/drop 会导致计数错乱 → 不是 `Send`；
- `RefCell<T>`：借用检查器是**非原子**的运行期计数 → 不是 `Sync`；
- `Arc<Mutex<T>>`：原子计数 + 互斥锁 → 同时满足 `Send + Sync`，是线程间共享可变状态的标准答案。

> 记忆锚点：`Send` 管「搬家」，`Sync` 管「合租」。编译器用这两个标记 trait 在编译期
> 拦截数据竞争 —— 这是「 fearless concurrency（无畏并发）」的技术底座。

## 五、`'static` 的两种含义（最容易混淆的概念）

实践课程：lesson_13 示例 7。

| 写法 | 含义 | 例子 |
| --- | --- | --- |
| `&'static T` | **引用本身**从程序启动活到结束（数据在二进制只读区） | `const APP: &str = "app"`、字符串字面量 |
| `T: 'static` | **类型 T 不包含任何短于 'static 的借用**（约束） | `Box<dyn Error>` 隐含 `Box<dyn Error + 'static>` |

判别口诀：写在**引用类型里**是「活多久」，写在**trait bound 里**是「不许带短期借用」。
`thread::spawn` 要求闭包 `F: Send + 'static`，正是在禁止子线程引用主线程的栈变量 ——
这就是 lesson_17 示例 2 必须用 `move` 的深层原因。

## 六、内部可变性的适用边界

实践课程：lesson_16 示例 5/6。

| 类型 | 检查时机 | 线程安全 | 用途 |
| --- | --- | --- | --- |
| `Cell<T>` | 编译期无检查（Copy 语义 get/set） | 否 | 单线程、小 Copy 值的「伪可变」 |
| `RefCell<T>` | **运行期**借用计数，违规 panic | 否 | 单线程 `Rc<RefCell<T>>` 组合 |
| `Mutex<T>` | 运行期加锁，阻塞等待 | 是 | 跨线程共享可变状态 |
| `RwLock<T>` | 运行期读共享/写独占 | 是 | 读多写少的跨线程数据 |

原则：内部可变性是**逃生舱，不是默认通道**。优先让所有权/借用设计直接表达可变性；
每次写下 `RefCell` 时，问一句「是不是我的所有权划分出了问题」。

## 七、unsafe Rust 的边界（概念课，本项目不写 unsafe 代码）

本仓库所有课程刻意保持零 `unsafe`（见 [.dsh/lesson-conventions.md](../../../.dsh/lesson-conventions.md)），
但初学者必须知道边界在哪里，才能读懂第三方文档。

`unsafe` 块解锁五种超能力：

1. 解引用裸指针（`*const T` / `*mut T`）；
2. 调用 `unsafe` 函数（含 FFI）；
3. 访问/修改可变静态变量；
4. 实现 `unsafe` trait（如 `Send`/`Sync` 的手工承诺）；
5. 访问 `union` 的字段。

**契约**：`unsafe` 不是「关闭检查」，而是把「这段代码维持内存安全」的责任从编译器转移到程序员。
标准库自身大量使用 `unsafe` 实现安全的抽象（如 `Vec` 的容量管理），对外暴露的全是安全 API ——
这也是「安全抽象封装不安全内核」的分层思想。

学习路径建议：先掌握全部安全 Rust（本项目 lesson_01~18），需要 FFI/嵌入式/性能极限时
再读 *The Rustonomicon*；日常应用开发几乎不需要手写 `unsafe`。

## 八、async/await 执行模型：从轮询到事件循环

实践落点：demoweb 全线使用 Tokio；本节解释它的运行原理。

```
async fn  →  编译器生成实现 Future 的状态机
Future::poll(cx)  →  Ready(值) 完成 / Pending 挂起并注册 Waker
事件循环（Tokio runtime）  →  就绪队列 + I/O 多路复用（epoll/IOCP）
Waker::wake()  →  把挂起的任务放回就绪队列，等待下次 poll
```

四个初学者必懂的推论：

1. **async 函数返回的是 Future**，不 `.await` 就一行代码都不会执行（惰性，同迭代器）；
2. **跨 `.await` 持有锁要谨慎**：标准 `Mutex` 守卫跨 await 会阻塞整个执行线程，异步上下文用 `tokio::sync::Mutex`；
3. **CPU 密集任务不要堵 async 线程**：用 `spawn_blocking` 挪到阻塞线程池 —— demoweb 的 bcrypt 密码哈希（`services/password.rs`）正是这样做的；
4. **`tokio::select!` 同时轮询多个分支**，任何分支先就绪就先执行 —— demoweb「踩坑记录 1」（优雅停机与请求竞争）就是这个语义的直接体现。

> async 与线程（lesson_17）的关系：线程是**操作系统调度**的并行单元，适合 CPU 密集；
> async 任务是**运行时调度**的并发单元，单个线程可承载数万任务，适合 I/O 密集。
> demoweb 两条都用：Tokio 承载 HTTP 并发，`spawn_blocking` 承载 CPU 密集。
